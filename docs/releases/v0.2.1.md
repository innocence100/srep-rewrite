# SREP-NG 0.2.1 release preparation

**Status: candidate preparation only—not published.** No v0.2.1 tag, release,
native package, or downloadable checksum has been produced by this work. The
published v0.2.0 release, tag, assets, URLs, and recorded hashes remain
unchanged. Do not use a v0.2.1 download URL until the parent release owner has
published and independently verified the actual release.

## Intended scope

This candidate carries the previously accepted sparse-input m3 optimization:
end-order fusion during pass 2, compact authenticated candidate/DP rows, and a
bounded optional predecessor directory. It preserves NGv3, matching semantics,
default m3 / index / xxh3 / 8 MiB blocks, and the existing 256 MiB managed
working-memory and 4 GiB temporary-storage defaults. No automatic resource
policy from the planned 0.3.0 work is included. Rust 1.88.0 remains the MSRV;
the package remains MIT-licensed, with dependency attribution governed by the
lockfile audit and package notices.

The optimization was source-reviewed and its prior native/CI validation passed
on source/tooling commit `4af679fd4292c3f864db1eb717e48f504e58e78a`; the final
evidence review was accepted (R-P4 PASS). This branch's production source and
algorithm tests are unchanged from that accepted source; the sole test change is
the `tests/release_cli.rs` package-version assertion updated from 0.2.0 to 0.2.1.
Prior evidence validates the accepted implementation at that earlier revision,
not a newly built v0.2.1 release binary.

## Candidate package contract

The native workflow is prepared to build three archives using the existing
portable package contract:

```text
srep-v0.2.1-x86_64-unknown-linux-gnu.tar.gz
srep-v0.2.1-x86_64-pc-windows-msvc.zip
srep-v0.2.1-aarch64-apple-darwin.tar.gz
```

Each requires a native build on Linux x86_64, Windows x86_64 MSVC, or macOS
ARM64, respectively. The six-job gate covers both Rust 1.88.0 and stable for
each platform; only MSRV jobs upload packages. Archives must retain the
established root layout and include the executable, `LICENSE`, `README.md`,
`CHANGELOG.md`, `THIRD_PARTY.md`, `THIRD_PARTY.audit`, `NOTICES`,
`BUILD-PROVENANCE.json`, and `PLATFORM-README.md` (`srep.exe` on Windows).
`SHA256SUMS` is distributed beside the archives. No platform ABI/runtime floor,
signature, notarization, or hash claim for these candidate assets is established
before the actual native runs.

## Required release gates (not performed here)

Before publication, the parent release owner must:

1. Review and commit this preparation, then run the six native jobs and ordinary
   CI on the exact clean source/tooling commit. Confirm all package contents,
   `--version`/help and extracted smoke results, provenance identities, license
   notices, and archive checksums. Windows and macOS evidence must come from
   GitHub Actions native runners.
2. Record the exact v0.2.1 source commit, Rust 1.88.0 package binary SHA-256s,
   archive SHA-256s, run IDs, target/runtime observations, and package smoke
   reports. Do not reuse v0.2.0 hashes or infer v0.2.1 binary identity from
   source equivalence.
3. Run the complete 72-row (`12 samples × 6 methods`) fidelity comparison on
   the actual extracted Linux v0.2.1 package binary with the established
   `--memory 256MiB --temp-limit 32GiB` acceptance settings. Require complete
   resource-success round trips and the unchanged `majority-final-xz-v1` gate;
   retain report, log, binary identity and SHA-256. Also repeat the 258 MiB
   default-settings round trip on that package. The historical measurements
   below do not satisfy either exact-package gate.
4. Before publication, prepare a candidate bundle manifest from the downloaded
   native Actions artifacts and the fresh v0.2.1 actual-package evidence. Check
   archive hashes and detached `SHA256SUMS`, extracted
   `BUILD-PROVENANCE.json`, and binary identities against native run records;
   independently review all gates before publishing. Keep the release marked
   prerelease unless the owner explicitly decides otherwise.
5. After publication, download the newly published release assets independently
   and verify each downloaded asset against the candidate manifest and
   checksums. Record a separate post-publication receipt with release/tag
   identity, download URLs, observed hashes, and verification results. Do not
   imply this receipt or verification exists before publication.

The full 72-row run and native Windows/macOS build/test/package steps were
deliberately not launched during this preparation. Linux cross-compilation, if
used separately, cannot replace native evidence.
