## Test inputs and resources

- Fidelity corpus: 12 samples × 6 methods (m0–m5) = 72 rows. Full runner wall
  ~9 h 31 m. Slow stages: sample 07 m0 compress ~3.5 h, sample 07 m3 compress
  ~2 h 57 m. The sample-07 cost comes from a 512 KiB sparse input whose m3
  managed temp ledger peaked at 9646868416 B = 9199.970642 MiB = 8.984346 GiB
  — small input, large lookup cost.
- Fidelity flags: `--memory 256MiB --temp-limit 32GiB --temp-dir <run>/temp`.
  The CLI 4 GiB default temp limit **can fail** this corpus (row 40 stopped
  with `TempBudgetExceeded` at 4 GiB); the explicit 32 GiB option was needed.
  Enough free space is required for the chosen temp budget; it is **not**
  required for all inputs.
- Large-258 recipe `repeat-1mib-separated-256mib-unique-v1` (270532608 bytes),
  defaults only (`--temp-dir` added, no method/layout/checksum overrides),
  default 4 GiB temp budget, no overrides.
- `--memory` is managed working memory, not RSS: input/output buffers,
  candidate storage, indexes, sorting, WIS/match selection, caches, and their
  working control state. File pathname processing, runtime and allocator
  overhead are excluded. Temp is an independent budget.
- Profile phase FD values are live counts, not peaks. RSS samples are
  optional and qualified where shown.

## QUALITY verdict: policy revision to `majority-final-xz-v1`

**This is an explicit user quality-policy change, not a concealed waiver.**
The user revised the fixed-corpus release gate to a per-method strict
majority: a method passes when strictly more than half of its 12 fixed rows
have a final-XZ stream strictly smaller than the frozen baseline (7/12 or
more; integer byte comparison; ties do not win). `coverage_geomean >= 0.95`,
complete 72 rows, round-trip and integrity protections remain gates. The old
`size_geomean <= 1.05` / `raw_size <= 1.10` limits are retained as
**diagnostics, not gates**.
