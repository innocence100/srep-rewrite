# v0.3.0 resource-default implementation evidence (local)

Status: local source implementation evidence, now extended by serial integration.
This is not a release record or native-platform verification claim.

## Scope delivered

- `src/main.rs`: retain explicit resource option origins, validate existing CLI
  constraints before file open, open file input once and classify its opened handle,
  then run the closure-based resource orchestration before staging. Existing
  `write_archive` and `finish_temporary_transaction` remain the publication path.
- `src/platform/`: pure memory/temp resolution, Linux bounded `/proc` parsing and
  visible cgroup ancestor collection, and fallible system-memory APIs for Windows
  and macOS.
- `docs/plans/v0.3.0-resource-defaults.md`: curated approved design summary.

## R1 temp-growth boundary coverage (added 2026-10-16)

Added tests only under `#[cfg(test)]` in the existing binary-private resolver and
orchestration test modules; production policy code was not changed. The pure
resolver test checks exact integer results for 4 GiB → 40 GiB and 8 GiB → 80
GiB; the 32 GiB floor boundary uses `floor(34359738368 / 10) = 3435973836`,
which yields 34359738360 and therefore keeps the 34359738368-byte floor; the
first length above it, 3435973837, yields 34359738370. The largest
non-overflowing input is `u64::MAX / 10 = 1844674407370955161`, yielding
18446744073709551610; the next length fails with existing
`InvalidConfiguration` and an error naming `--temp-limit`.

A second test reaches the actual `run_compress_orchestration` helper with
`InputKind::Regular`, logical length 8 GiB, an explicit memory budget, no
explicit temp limit, and a panicking host probe. It asserts the transaction is
entered once with an 80 GiB temp limit, proving the policy formula is applied
without metadata-backed multi-EiB files or host probing.

Exact focused command/status logs are in
`/tmp/opencode/srep-030-reports/core/r1-growth/`. Rust 1.88.0 format, locked
binary check, Clippy (`-D warnings`), and debug/release `--bin srep` tests passed;
both test profiles report 22 passed, 0 failed, 0 ignored for the `srep` binary
test target. This focused test run used the pre-final release CLI binary with
SHA-256 `68294eadf7f937d7eb7cd2678bd76c8ed6c0c1a418578473e5c8542265d94bda`.
The later 72-row fidelity, paired 258 MiB roundtrips, and default-resource
acceptance run below also used that binary; the two `#[cfg(test)]` additions do
