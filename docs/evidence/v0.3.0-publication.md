The unchanged inherited sparse report describes fixed 256 MiB / 32 GiB,
sample07 **development binaries labelled 0.2.0**: time 10638.203 → 4298.326 s
(-59.6%), managed temp 9646868416 → 6029489688 B (-37.5%). These are not fresh
0.2.1/0.3.0 timings or universal speedups. Raising/selecting a budget is not a
RAM-utilization algorithm redesign. The 0.2.1 fixed default temp is still 4 GiB,
below this sample's managed peak; comparison runs explicitly used 32 GiB.

0.3.0 compress selects half **physical total**, not available RAM, clipped by
identified hard limits; incomplete detection uses ≤256 MiB fallback with stderr
warning even when quiet. Auto temp is max(32 GiB, 10× regular input length), or
32 GiB for stdin/nonregular input; overflow needs an explicit override. Flags
override resources independently. Other commands/library retain 256 MiB / 4 GiB.
Budgets are managed ledgers, not RSS caps, reservations or runtime budget growth.
Linux's actual acceptance observed fallback/auto origins in an 8 GiB-capped
Ubuntu24.04 container; native Windows/macOS auto observations do not independently
measure physical totals. Missing cgroup visibility can also cause ordinary-host
fallback; RLIMIT_AS, Windows Job and macOS container limits are not fully detected.

Linux has observed GLIBC_2.34 requirement (host glibc2.31 could not load it).
Windows is MSVC, with VCRUNTIME140.dll imports. macOS ARM64 has ad-hoc signature
flags 0x20002, no publisher signing identity, and no notarization. Container
Linux execution is not Windows/macOS native evidence.
